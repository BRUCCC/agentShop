# 分层读取：先确认相关，再打开要改的文件

面试用 15 分钟。建议先讲推广通里的真实用法，再用这个仓库演示同一套分层。仓库是去识别化之后的示意项目，业务换成了广告前端，分层方式和当时的知识库一致。

远程仓库：<https://github.com/BRUCCC/RAG-DEMO>

## 这套 workflow 怎么走

部门的 AI 研发 Harness 里有一套按目录存放的 Markdown。模型不读整仓。加载分三层：

| 层 | 推广通里放什么 | 本仓库对应文件 |
| --- | --- | --- |
| L0 | 文首 `brief`、仓库名、关键词。只用来决定要不要打开 | [`.abstract.md`](knowledge/resources/ad-frontend/feed-card/.abstract.md) |
| L1 | 工程约束、页面入口、功能到目录的索引、PRD 落点 | [`.overview.md`](knowledge/resources/ad-frontend/feed-card/.overview.md) |
| L2 | 索引指到的具体文件。真的要改时才读 | [`card.md`](knowledge/resources/ad-frontend/feed-card/card.md)、[`exposure.md`](knowledge/resources/ad-frontend/feed-card/exposure.md) |

本仓库把这三层做成可检索的 demo。检索实现见 [`ad_rag/retriever.py`](ad_rag/retriever.py)，目录读取见 [`ad_rag/ragfs.py`](ad_rag/ragfs.py)，Milvus 混合检索见 [`ad_rag/milvus_store.py`](ad_rag/milvus_store.py)。

1. `python -m ad_rag ingest` 只索引含正文的目录。L0、L1 各做一条稠密向量，关键词交给 Milvus 内置 BM25。
2. 粗排：L0 的向量和 BM25 用 `hybrid_search` 加 `RRFRanker` 召回候选目录。
3. 精排：只在这些候选上，用 L1 的向量和 BM25 加 `WeightedRanker` 重排。
4. 命中之后才把 L2 拼进上下文，交给上层 agent。入口是 [`AdFrontendRAG.retrieve`](ad_rag/agent.py)。
5. `python -m ad_rag eval` 用 12 道标注题看准确率、召回率和高相关命中率，计算在 [`ad_rag/metrics.py`](ad_rag/metrics.py)。

现场可以跑：

```bash
python -m ad_rag search "开屏全屏广告的跳过按钮放哪"
python -m ad_rag ask "写一个带广告标识的信息流卡片，并做曝光"
python -m ad_rag eval
```

`search` 同时打印粗排和精排。`ask` 的输出就是模型真正拿到的上下文。运行说明见 [README.md](README.md)。分层概念参照 [OpenViking](https://github.com/volcengine/OpenViking)。

## 1. 它解决什么问题

推广通同时覆盖到餐、到综、酒店，又是 PC 和 App 双端。页面看起来像，真正该改的仓库和目录经常不是同一处。

没有这套文档时，我会把 PRD 和一大段代码直接塞给模型。它经常只改 PC、不改 App，或者改到应用仓里那层组装，没改真正的公共 Hooks。到餐和到综的逻辑也会被写进同一个分支。返工主要花在找仓库和补另一端，不是花在写组件。

## 2. 它怎么运作

知识库是一批 Markdown，按业务目录放，不把整仓读进上下文。加载分三层：

- **L0：** 文首的 `brief`、仓库名和关键词。检索时先看这段，用来决定要不要打开。
- **L1：** 工程约束、页面入口、功能到目录的索引、PRD 改动会落到哪个仓库。确认相关后才读。
- **L2：** 索引指到的具体文件。只有真的要改时才读。

推广通创编的文档是这样的：

```markdown
---
brief: 推广通创编。字段联动、校验、提交放在公共 Hooks；PC 平铺和 App 抽屉只拆 UI。
repos:
  - tuiguangtong-create
keywords: [推广通, 创编, 定向, 出价, 双端同构]
---

# 推广通创编

## 工程约束
- 改联动、校验、提交时，改公共 Hooks，PC 和 App 入口一起看。
- PC 平铺、App 抽屉只改各自的容器，不把布局写进 Hooks。
- 应用仓如果只是消费公共 Hooks，优先升版本，不在页面里复制一份。

## 功能到目录
| 功能 | 目录 |
| --- | --- |
| 定向、出价、校验、提交 | src/hooks/useAdCreate、src/hooks/useTargeting |
| PC 平铺容器 | src/pages/create/pc |
| App 抽屉容器 | src/pages/create/app |

## PRD 落点
| PRD 改动 | 主改位置 | 另一端 |
| --- | --- | --- |
| 字段联动、校验、提交 | 公共 Hooks | PC 和 App 都要接 |
| 只改平铺或抽屉布局 | 对应端的容器 | 不改 Hooks |
```

实际跑的时候，PRD 里出现「定向」「创编」会先命中这段 brief。模型和约束对得上，再按表格打开 Hooks。只改 PC 布局时，文档写明不要动 Hooks。

本仓库用同一顺序演示。查询先打到目录的 `.abstract.md`，精排再读 `.overview.md` 里的导航，最后才加载 `card.md` 这类正文。`python -m ad_rag search` 能看到前两层的排序差，`ask` 才会带上 L2。

## 3. 它好在哪里

模型只能根据这次上下文里真的出现的内容做判断。整仓塞进去，双端约束会被别的代码冲淡；上下文里没有这条约束，它就按最常见的单端页面去改。

L0 把「要不要读」和「读完改哪」拆开。检索先用很短的 brief 做筛选，命中后再读禁止项和目录。模型的注意力留在当前改动上，仓库位置来自文档，不是凭文件名猜。

Harness 是模型外面的这一层：什么时候检索、读到哪一层、哪些约束必须进上下文。知识库只负责把对的上下文送进去。

## 4. 它怎么演化来的

第一版是一篇长 README，业务说明、目录和约束混在一起。模型经常读到后半段就丢掉开头的双端要求，到餐和到综的页面也会改串。

后来改成目录加文首 brief。检索只比对 brief，相关才打开正文。

还有一次文档只写了「注意双端」。模型仍然只提交了 PC。后来把这句话改成硬约束：改联动、校验、提交必须看公共 Hooks，并且 PC 和 App 入口一起看；只改布局才动对应端的容器。推广通的新页面复用这套写法，先写约束和目录，再让模型改代码。

示意项目里也能看出这次改法：L0 只留短句做筛选，L1 写成「改什么、不改什么、文件在哪」，而不是一句提醒。

## 5. 它的限制

文档落后于代码时会失效。人把目录挪了、文档没改，模型会改到旧文件。

brief 写得太泛，不相关的文档也会被打开。所以正文里要写清什么改动不要召回，例如只改订单页时不要打开创编文档。

新业务还没有文档时，它提供不了帮助，只能先由人补一页，或者退回人工指定仓库。

它也不负责判断金额、权限、接口协议能不能改，这些仍然要人看。知识库不执行改动，也不代替代码评审。

评测同样有边界。本仓库的 `eval` 只统计检索有没有打开对的目录，不证明生成的代码能通过业务评审。

## 6. 哪些是自己设计的

部门 Harness 里，检索、按路径读文件、改仓库是现成能力。我参与的是这条线的 RAG 选型，以及选型之后知识怎么写。

选型参考了 [OpenViking](https://github.com/volcengine/OpenViking) 的文件系统，没有把整仓或一个只给程序读的库当成上下文来源。核心是 L0 / L1 / L2 按需加载。资源写入时，系统把原文收成三层，每个目录生成 `.abstract` 和 `.overview`，从根到叶都有摘要：

| 层 | 大约篇幅 | 给 Agent 做什么 |
| --- | --- | --- |
| L0 摘要 | 约 100 tokens，一句话 | 判断这个目录有没有关系。无关就停，不读后面两层 |
| L1 概览 | 约 2,000 tokens | 看核心信息和使用场景，决定改哪里 |
| L2 全文 | 原始内容 | 只有要深入修改时才打开 |

多数查询读到 L1 就能做完规划，Token 留在当前改动上。这和 Skills 的渐进式披露是同一件事：Agent 先看轻量元信息，确认需要再逐层取全文。

知识的正文用 Markdown。人可以直接读、改、纠正 Agent 用的知识，也可以用 Git 回看和回滚。Agent 有 `write_file` 之后，可以在工作分支上补条目和索引，再经审核合入主库。会话结束时，系统可以提议把用户偏好写入 `user/memories/`，把操作记录写入 `agent/memories/`。偏好仍是用户知识。操作记录要经过结果评价、跨轨迹归纳和后续验证，才算可靠经验，不能把一次操作直接写进主库。

`.abstract` / `.overview` 解决的是从上到下的摘要。文件之间还要有横向链接，否则拆得越细越难找。知识库按 Wikipedia 来组织：条目提到别的条目时用链接指向它，目录另有入口页和索引页。Agent 可以顺着链接从一个概念走到相关概念。这是用文件链接承担一部分 GraphRAG 里的关系导航，而不必先建一张实体图谱。

模型会不会自己维护这些链接，差别很大。能力强的模型写新条目时会回指已有条目，并顺手改索引；不少模型只会孤立追加文件。所以负责写入的提示词里把动作写死：每新增一条，先检索并链接到相关旧条目，再更新所在目录的索引页，让两边都走得到。

投放文档的内容也是我维护的：目录怎么分、brief 写什么、每层放多少、双端约束怎么写成禁止项、PRD 改动落到哪个目录。这些来自推广通创编的实际改法。

这个仓库演示的是选型之后的读路径。Markdown 仍是正文，[Milvus](https://milvus.io/docs/hybrid_search.md) 只索引 L0 和 L1，用来决定先打开哪个目录。各目录 `.overview.md` 里的「快速导航」就是横向索引的缩小版。自动写入 `memories/`、以及写入时强制双向链接，留在真实 Harness 的写入提示里；示意项目只把「先摘要、再概览、最后全文」跑通。
