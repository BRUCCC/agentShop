# 测试用例

对照现在这版商店。范围是加购、三种下单、结算和优惠。24 小时锁放在最后，用改到期时间的办法，不必真等一天。

不测加分题、福袋、开卖时间、并发抢购，也不测 MCP。价格只看接口和页面上的应付，不看毛利率。

先在项目目录运行 `npm run dev`，打开 `http://localhost:3000`。测外部 API 时用没有本店 cookie 的客户端，例如新的 `curl` 或一段不带 cookie 的 `fetch`。浏览器若已经打开过 `/?as=agent`，先访问 `/?as=human`，否则这个浏览器里的请求会被当成 AI 下单。

每条用例测完，购物车里会留下商品，库存也会因成交而减少。下一组用例开始前，把购物车清空，或换一个没有 cookie 的客户端。

## 价格怎么算

折前小计 = 标价 × 数量，多件相加。门槛只看折前小计。

1. 折前小计满 1000，商品金额减 100。未满不减。
2. 渠道是 `agent` 时，把减完后的商品金额乘 0.95，四舍五入到整数。`.5` 进位。人类渠道不乘。
3. 折前小计满 990，运费 0，否则运费 100。运费不参加 95 折。
4. 应付 = 折后商品金额 + 运费。

页面上的「优惠」是折前小计和折后商品金额的差，所以 agent 的优惠里含满减和 95 折。

| 商品 | 折前小计 | 人类应付 | AI 应付 |
| --- | ---: | ---: | ---: |
| P006 × 1，标价 390 | 390 | 490 | 471 |
| P010 × 1，标价 0 | 0 | 100 | 100 |
| P004 × 1，标价 890 | 890 | 990 | 946 |
| P017 × 1，标价 990 | 990 | 990 | 941 |
| P001 × 1，标价 1890 | 1890 | 1790 | 1701 |
| P006 × 1 + P009 × 1，390 + 780 | 1170 | 1070 | 1017 |

P006 的分项：人类优惠 0、运费 100。AI 优惠 19、运费 100。

## 1. 加购物车

普通访问，地址栏不要带 `as=agent`。页头下不应出现「当前是 AI 下单」。

### TC-CART-01 从商品页加入

1. 打开 P006「磁吸手機支架」。
2. 数量保持 1，点「加入购物车」。

预期：进入购物车，只有 P006，数量 1，标价合计 NT$390。购物车件数变成 1。没有订单。

### TC-CART-02 只说加入购物车时，对话栏不下单

1. 先清空购物车。
2. 在右侧对话栏说：`把 P006 加入购物车`。不要出现「下单」「结账」「付款」。

预期：回复说明已经放进购物车。页面购物车出现 P006。没有新订单，确认页也不会自己打开。

### TC-CART-03 同名商品按 id 区分

1. 搜索「耳機」。
2. 确认结果里同时有 P001 和 P002，名称都是「Aero 無線藍牙耳機」，标价分别是 NT$1,890 和 NT$1,790。
3. 打开 P001 的商品页加入购物车。

预期：购物车里是 P001，标价 NT$1,890。不会被换成 P002。

### TC-CART-04 不能卖的商品加不进去

1. 打开 P002。库存为 0。
2. 再打开 P008「USB-C 編織充電線」。库存小于 0。
3. 分别尝试加入购物车。

预期：两件都加不进去，购物车内容不变。P002 仍能被搜到。

### TC-CART-05 标价为 0 仍可加入

1. 打开 P010「陶瓷手沖濾杯組」，标价 NT$0。
2. 加入购物车并查看报价。

预期：可以加入。人类渠道优惠 0、运费 NT$100、应付 NT$100。

### TC-CART-06 改数量和移除

1. 购物车里放 P006，把数量改成 2，再改回 1。
2. 点移除。

预期：数量 2 时标价合计 NT$780。移除后购物车是空的，件数是 0。两步都不产生订单。

### TC-CART-07 外部 API 只加购

用无 cookie 的客户端：

1. `POST /api/carts`，正文 `{ "channel": "agent" }`。记下 `id`。
2. 看响应头，不应出现 `cart_id` cookie。
3. `PUT /api/carts/{id}/items`，正文 `{ "product_id": "P006", "quantity": 1 }`。
4. 不要调用 checkout。
5. 刷新普通网页的购物车。

预期：接口返回的车里有 P006，`channel` 是 `agent`。网页那辆车不变。没有订单。

## 2. 优惠

报价用 `POST /api/quotes`。它不改购物车，也不锁库存。响应里有 `queried_at`，没有 `margin_rate`。

### TC-PRICE-01 未满门槛

`channel` 用 `human`，商品 P006 × 1。

预期：`subtotal` 390，`discount` 0，`shipping_fee` 100，`total` 490。

再把 `channel` 改成 `agent`。

预期：`discount` 19，`shipping_fee` 100，`total` 471。

### TC-PRICE-02 刚好免运，但没有满减

P017 × 1，折前小计 990。

预期：人类 `total` 990，运费 0，优惠 0。AI `total` 941，运费 0，优惠 49。

### TC-PRICE-03 满减后再看渠道

P001 × 1，折前小计 1890。

预期：人类 `total` 1790。AI `total` 1701。两边运费都是 0。

### TC-PRICE-04 两件一起才跨过门槛

购物车同时放入 P006 和 P009。

1. 只勾选 P006，看右侧金额。
2. 两件都勾选，再看金额。

预期：只选 P006 时，人类应付 NT$490。两件都选时折前小计 NT$1,170，人类应付 NT$1,070，运费 0。未勾选的商品不进这组报价。

### TC-PRICE-05 页面和接口是同一套数

普通访问下，把 TC-PRICE-01 的人类结果和购物车页面对照。

预期：页面是标价合计 NT$390、优惠 NT$0、运费 NT$100、应付 NT$490。对话栏不出现「95 折」。

## 3. 三种下单

三种入口可以买同一件 P006。差别在渠道和应付，不在商品。

| 入口 | 怎么开始 | 渠道 | P006 × 1 应付 |
| --- | --- | --- | --- |
| 普通网页 | 直接打开首页 | human | 490 |
| 页内对话 | 普通网页里说「帮我下单」 | human | 490 |
| 本地 AI 页面 | 打开 `/?as=agent` | agent | 471 |
| 外部 API | `POST /api/carts` 后 checkout | agent | 471 |

### TC-ORDER-01 网页结账是人类价

1. 普通访问，购物车只放 P006 × 1。
2. 去结账，点「模拟付款」。

预期：确认页应付 NT$471 不应出现。应付是 NT$490。付款后购物车清空，出现订单。订单 `channel` 是 `human`，`total` 是 490。

### TC-ORDER-02 页内对话下单也是人类价

1. 普通访问，购物车只放 P006 × 1。
2. 对话栏说：`帮我下单`。

预期：生成人类订单，应付 490。只说「加入购物车」的那一轮不能产生这张订单。顾客这句话里要有「下单」「结账」或「付款」这类用语。

### TC-ORDER-03 本地页面按 AI 下单

1. 打开 `http://localhost:3000/?as=agent`。地址栏里的 `as` 会被拿掉。
2. 确认页头下有「当前是 AI 下单」。
3. 加入 P006，去结账。

预期：购物车和确认页都是优惠 NT$19、运费 NT$100、应付 NT$471。对话栏写明满减后再享 95 折。模拟付款后的订单 `channel` 是 `agent`，`total` 是 471。

### TC-ORDER-04 清掉标识后恢复人类价

1. 接上一条，若购物车里还有 P006，打开 `http://localhost:3000/?as=human`。
2. 若上一条已经付款，重新加入 P006。

预期：「当前是 AI 下单」消失。同一件商品应付回到 NT$490，对话栏不再写 95 折。

### TC-ORDER-05 外部 API 直接下单

无 cookie 客户端：

1. `POST /api/carts`，正文 `{ "channel": "agent" }`。
2. `PUT /api/carts/{id}/items`，P006 数量 1。
3. `POST /api/carts/{id}/checkout`，正文 `{ "product_ids": ["P006"] }`。

预期：响应 `channel` 是 `agent`，`total` 是 471。这次请求不要求对话里出现「下单」。浏览器里的购物车不被这张单清空。

### TC-ORDER-06 外部车和网页车互不占用

1. 浏览器普通访问，加入 P001，先不要付款。
2. 用无 cookie 客户端按 TC-ORDER-05 买 P006。
3. 回到浏览器购物车。

预期：浏览器里仍是 P001，应付按人类价 NT$1,790。P006 的 AI 订单单独存在。

## 4. 结算

### TC-PAY-01 只结算勾选的商品

1. 普通访问，购物车放入 P001 和 P006。
2. 只勾选 P006，去结账并付款。

预期：这张订单只有 P006，应付 NT$490。购物车里还留着 P001。P001 没有被下单。

### TC-PAY-02 外部接口也可以只结算一部分

agent 车里同时放入 P001 和 P006。`POST /api/carts/{id}/checkout` 的正文只传 `{ "product_ids": ["P006"] }`。

预期：订单只有 P006，`total` 471。再 `GET /api/carts/{id}`，车仍是 `open`，里面还剩 P001。

### TC-PAY-03 整车再次结账不重复扣

1. 对只剩一件商品的车做一次不带 `product_ids` 的 checkout。
2. 用同一个 `cart_id` 再 checkout 一次。

预期：第二次返回第一次那张订单，`id` 相同。该商品的可售数量只减少一次。

### TC-PAY-04 空车不能结账

对没有商品的 `cart_id` 调用 checkout。

预期：请求失败，不产生订单。

## 5. 24 小时锁

加购、报价、网页上的「模拟付款」都不会锁库存。锁只在建立交接时出现。链接可以一直打开，锁和锁价只保留 24 小时。

下面用人类渠道。若要看 AI 锁价，先打开 `/?as=agent`，再在对话栏要求保留商品。锁价应变成 471，其余步骤相同。

### TC-LOCK-01 加购当时不锁

1. 普通访问，只把 P006 放入购物车。
2. 看 `data/shop.sqlite` 的 `reservations`，条件是这辆车且 `status = 'held'`。

预期：没有未过期的 `held` 记录。商品页可售数量不因这辆购物车减少。

### TC-LOCK-02 建立交接才锁 24 小时

1. 购物车只放 P006。
2. `POST /api/carts/{id}/handoff`。
3. 打开返回的 `url`，形如 `/checkout/{token}`。

预期：

- 返回的 `expires_at` 比 `reserved_at` 晚 24 小时。
- 确认页显示人类锁价，应付 NT$490。
- `GET /api/handoffs/{token}` 的 `expired` 是 false，`quote.total` 是 490。
- 数据库里这辆车有 `held` 预留，`reserved_at` 和 `expires_at` 都有值。
- 这一步没有订单。

P006 的可售数量比锁之前少 1。另一辆车再买这 1 件时，不能占用这一份预留。

### TC-LOCK-03 改购物车会放开锁

1. 接上一条，把 P006 的数量改成 2，或再加入另一件商品。
2. 再次打开同一个确认链接。

预期：旧的 `held` 预留被释放。链接仍能打开，但不再使用刚才锁住的 490。页面按当前购物车重新报价。链接地址没有变。

### TC-LOCK-04 锁定期内付款沿用锁价

1. 重新对只含 P006 的人类车建立交接。
2. 在确认页点「模拟付款」。
3. 再打开同一个链接。

预期：订单应付 NT$490，`channel` 是 `human`。预留变为 `consumed`。再次打开链接看到的是这张订单，而不是一张新订单。可售数量不重复扣。

### TC-LOCK-05 到期后链接还在，锁价失效

不必等待 24 小时。交接成功后，把这辆车未消费的预留改到过去：

```js
const { DatabaseSync } = require("node:sqlite");
const db = new DatabaseSync("data/shop.sqlite");
const cartId = "这里换成购物车 id";
const past = new Date(Date.now() - 60 * 1000).toISOString();
db.prepare("UPDATE reservations SET expires_at = ? WHERE cart_id = ? AND status = 'held'").run(past, cartId);
```

然后立刻 `GET /api/handoffs/{token}`，并在浏览器打开 `/checkout/{token}`。

预期：

- 链接仍能打开。
- `expired` 是 true。
- 预留状态变成 `released`。
- 报价改按当前目录重算。车里仍是 P006 × 1 时，人类应付回到 490，但这是新报价，不是过期前那份快照。
- 若此时库存已经不够，页面列出缺少的商品，不换成另一件。

可售数量在 `expires_at` 过去后就不再扣除这份预留，不用等后台那次定时释放。

## 建议顺序

先跑 TC-CART-01、TC-PRICE-01、TC-ORDER-01、TC-ORDER-03、TC-ORDER-05。这五条能确认加购、人类价、本地 AI 价和外部 API 价。

然后跑 TC-CART-03、TC-PAY-01、TC-LOCK-02、TC-LOCK-05。这四条覆盖同名商品、部分结算和锁。

对话栏用例需要可用的 API key。没有 key 时，网页和外部 API 的用例仍然可以先测。
