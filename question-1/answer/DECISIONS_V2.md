## 0. 谁才算 agent 下单

- 状态：调整
- 原本的需求：由 AI 助理建立的訂單一律再打 95 折，鼓勵顧客使用 AI 購物。
- 我的假设：先前把网页右侧的对话栏当成 agent。这个理解不对。页内对话仍然是人在自己的浏览器里操作。
- 我的判断：网页内的 AI 对话窗口保留，但视作人类下单，不享受 agent 优惠。外部 agent 通过 Web API 下单，才算 agent 订单，与人类订单区分。
- 我做的取舍：页内对话的报价、交接和结账都用 `human`。95 折只给外部 API 创建的 agent 订单。不再因为顾客在对话栏里说下单，就把这笔订单标成 agent。
- 我会怎么回复 PM：店里的对话框是给人用的，按人类订单计价。ChatGPT 这类外部助理走有文档的 API，那一单才是 AI 订单，才有 95 折。

## 1. 查询时间

- 状态：接受
- 原本的需求：AI 助理查到的價格和庫存要附上查詢時間，避免 AI 拿舊資料跟顧客報價。
- 我的假设：时间只说明这一次响应是什么时候的价格和库存。v0.2 没有改写的预留 24 小时、链接不过期，继续有效。
- 我的判断：加上查询时间。时间相关的产品逻辑按照新版本走。
- 我做的取舍：商品、库存和报价都返回 `queried_at`。不加开卖时间，因为福袋和加分题先不做。
- 我会怎么回复 PM：每次把价格和库存交给助理时都带查询时间。助理要用这一次的数字，不要拿对话里更早的报价。

## 2. 购物车和订单来源

- 状态：调整

- 我会怎么回复 PM：客服和行销只看两类。页面上完成的是人类订单。外部助理通过 API 完成的是 agent 订单。

## 3. 外部 agent 怎么进店

- 状态：调整

## 11. 直接下单、毛利和 1000 件以上的推荐

- 状态：调整
- 原本的需求：為了減少流失，AI 助理建立購物車後，應該直接幫顧客完成下單，不需要顧客再操作。商品搜尋結果依「推薦分數」排序。行銷希望把高毛利商品的推薦分數乘以 1.5，但不需要讓 AI 助理或顧客知道。商品數未來會成長到 10 萬件。AI 助理查詢時，一次回傳全部商品，讓 AI 自己判斷比較快。
- 我的假设：外部 agent 调用下单接口，就是顾客通过自己的助理确认要买。页内对话栏不是这个场景。
- 我的判断：提供给外部 agent 时可以做直接下单。高毛利只是提高推荐分，排序不按毛利率，仍按推荐分，这个方法不变。1000 件以上先走 RAG，把命中的内容交给模型。
- 我做的取舍：页内对话栏仍然只在顾客明确说下单时才下单，而且按下单结果是人类订单。外部 API 提供下单接口，按下单结果是 agent 订单。不返回毛利率，也不改成按毛利率排序。不再用「1000 件以上由推荐算法排序、模型不能改顺序」那条。检索在服务端完成，命中的一页交给模型比较，一次仍不返回全部商品。
- 我会怎么回复 PM：外部助理可以替顾客直接下单。高毛利不单独拿来排序，排序还是看推荐分。商品变多以后也是先检索，再把命中的商品交给模型判断，不会一次把 10 万件塞给它。

## 12. 本地页面上的 AI 下单

- 状态：接受
- 原本的需求：请部署到一个我们可连线的网址；若无法部署，至少要能一个指令在本机启动。面试前，我们会用自己的 AI agent 来逛你的商店。
- 我的假设：demo 阶段没有线上服务。第三方 agent 可以打开本机页面，但不能靠人的普通访问去拿 95 折。
- 我的判断：Web API 仍是正式入口。另外提供本地页面：打开 `/?as=agent` 后，网页带上 AI 下单标识，这辆车按 agent 计价。打开 `/?as=human` 恢复人类价格。
- 我做的取舍：标识存在 `shop_actor`。只有带着它的浏览器会话享受 95 折。普通访问和页内对话仍是人类订单。
- 我会怎么回复 PM：没有线上地址时，助理打开本机的 AI 入口就能自己逛完并下单。页面会显示这是 AI 下单，并按 95 折计算。
